## Что изменилось для пользователя

В **Библиотеки → Ресурсы проекта** можно выбрать общую папку исходника и данных. Для структуры `project/figures/figure.tex` и `project/data/curve.dat` это `project`; TeX продолжает разрешать `../data/curve.dat` от папки исходника. Автоматического расширения до родительских каталогов нет. Выбор действует на открытый документ и сбрасывается при Open; после смены папки нужна новая сборка.

В реальном Linux-сеансе системный folder picker вернул отмену без видимого диалога. Поэтому добавлены поле пути и **Применить** / Enter. Пикер и ручной ввод используют один валидатор: каталог должен существовать и содержать исходник. Пустое значение не означает текущую рабочую папку; пробелы в именах не обрезаются. Неудачная попытка не меняет действующую папку. Во время сборки эти действия недоступны. Это проверенный ручной маршрут; системный диалог в этом окружении не объявляется рабочим.

CLI принимает `--project-root <dir>` вместе с `--log`, в любом порядке. Дубли, неизвестные параметры и отсутствующие значения отклоняются. Неподтверждённые входы дают exit 5 до изменения целевого PDF. [Инструкция пользователя](../docs/PROJECT_INPUT_VERIFICATION_RU.md) содержит GUI- и CLI-примеры и ограничения.

## Контракт входных файлов

До запуска TeX рабочий поток фиксирует SHA-256 обычных файлов выбранной папки. После компиляции список реально использованных локальных файлов берётся из `.fls` и сверяется с начальным снимком. Обычный post-build snapshot сам по себе теперь имеет статус Unverified. Для принятия PDF нужны подтверждённые входы, соответствующий исходник и актуальные контрольные суммы.

Регрессия с управляемым тестовым движком воспроизводит прежнюю ошибку: движок прочитал `.dat`, файл заменили байтами той же длины, затем движок завершился. Один снимок после сборки выглядел бы свежим; новая проверка отклоняет такой результат. Проверены также новый или исчезнувший вход, неверная папка, неполный recorder и ссылки. GUI и OneFigureSession сохраняют прежний корректный PDF, не продвигая неподтверждённый кандидат; CLI не заменяет существующий выход. Перед экспортом файлы проверяются повторно; маршрут с системным save picker проверяет их до и после диалога.

Обход ограничен 4096 файлами, 16384 записями каталогов, 4096 каталогами и глубиной 64; чтение — 64 МиБ на файл и 256 МиБ суммарно, recorder — 8 МиБ. Учитываются реально прочитанные байты, в том числе при росте файла после чтения metadata. Превышение лимита, ошибка чтения или неподдержанный вход не дают успешного подтверждения. Отмена и тайм-аут учитываются при обходе и чтении. Хеширование не выполняется в каждом кадре GUI.

**Граница гарантии:** это сравнение состояния до и после сборки, а не неизменяемая копия входов. Изменение с восстановлением прежних байтов между наблюдениями может остаться незамеченным. Внешние ресурсы TeX вне выбранного проекта явно непроверенные; состояние всей TeX-установки не сертифицировано. Внутренние символьные ссылки пока не поддержаны для подтверждения; системные aliases над корнем, например `/var` на macOS, обработаны отдельно. Полная гарантия соответствия произвольно меняющимся входам требует следующего контракта неизменяемых данных.

Исходные 75 файлов QA-копии сверены и восстановлены; Git corpus не изменён.

Экспортированный через toolbar GUI PDF: **19856 bytes**, одна страница, встроенный subset `STIXTwoMath-Regular` с Unicode mapping. SHA-256: `81c90e9dd27f68aafd5a32cfd8d48170e6e8bd680cb8a31dfd51a44e2729b5bb`. Этот хеш остался тем же после отказа повторного экспорта при изменённом `.dat`. Preview просмотрен в реальном приложении. Единственное видимое сообщение компилятора — `Package shellesc Warning: Shell escape disabled on input line 73`; исходный PNG сохранён, ошибка TeX не объявлялась.

CLI positive PDF имеет собственный SHA-256 `9b423442bbe9100f1c56677c83de98585099205e57392711d1ac57d3aee93a1d`. Разные PDF-run hashes не приравниваются к разным исходникам. CLI negative destination до/после: `032ea3a0e15e4aa753a80ee5c936542251581d7b772369f0018acd673461c2c6`.

Использован уже установленный `/usr/bin/xelatex` с изолированными QA-ресурсами Debian и STIX из ранее проверенного manifest. Формат, fontconfig и caches находятся в рабочей QA-папке. Системная TeX/font-конфигурация, Windows, MiKTeX и FlowBridge не изменялись. Версии, контрольные суммы и activation script сохранены в evidence; это описание QA-окружения, не универсальный установщик.

## Делегирование и следующий шаг

Реально работали узкие subagents **gpt-6-luna, high**: `/root/build_provenance` — core baseline/regressions и затем отдельно ручной root UI; `/root/drive_checkpoints` — Drive, CLI и изолированная TeX QA; `/root/recover_build_env` — восстановление toolchain/repo, независимый review и точный hosted CI audit. Одновременного владения одним исходным файлом не было. Root интегрировал, исправил actual-byte budget и responsive UI, выполнил финальный прогон, реальную GUI-проверку и публикацию.

**Следующий исполнимый блок — SCI-QA/SCI-PGF:** native compact Inspector → минимальная правка настоящего PGFPlots исходника → Undo → Save → XeLaTeX → export, с оригинальными .tex/PDF/PNG и пересмотром соответствующих native QA scripts. После их проверки обновлять APP_TREE и повторять suites. Не переносить Linux subset на physical Win10, IME или DPI. Контракт неизменяемых build inputs, полный G3, SCI142/AI88 и дополнительные научные движки остаются в scope; дальнейшие предметные этапы не опережают научную приёмку.
