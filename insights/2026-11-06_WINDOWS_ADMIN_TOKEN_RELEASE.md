## Security invariant implemented in this candidate

- Local Administrators SID membership, enabled Administrator role, TokenElevation, TokenIntegrityLevel RID, TokenElevationType, TokenLinkedToken presence and session ID are **separate fields**. IsInRole(Administrator) is not proof of current token elevation or account membership. A normal UAC-filtered medium token of the same local administrator is eligible for normal external MiKTeX.
- New live Windows read-only token diagnostic probes Win32 GetTokenInformation classes 18/19/20/25, integrity SID and session, and stores evidence in hosted and dedicated-main reports; a linked token is labelled **PRESENT_UNVALIDATED**, never proof of a usable child launcher. Elevated/high/unknown token blocks external MiKTeX preflight. Session 0 blocks interactive QA separately.
- Core production XeLaTeX version probe, direct build spawn and TeX package helper now call a read-only GetTokenInformation TokenElevation+TokenIntegrityLevel fail-closed guard. No TeX invocation with elevated/high or unreadable token, even when --disable-installer and --no-shell-escape are configured. The entire GUI process is not elevated or lowered by TikZarium.
- A narrow same-administrator filtered-token child launcher is **NOT_IMPLEMENTED, NOT_ACCEPTED**. CreateProcessWithTokenW requires SeImpersonatePrivilege and careful cwd/environment/handles/profile/cancellation; presence of TokenLinkedToken is not the same as a safe child. The built-in Administrator may have only a full unlinked token. CreateRestrictedToken alone is NOT equivalent to a UAC-filtered standard token, nor proof that MiKTeX permits execution.

Microsoft reference contracts: [TOKEN_ELEVATION_TYPE](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_elevation_type), [GetTokenInformation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation), [CreateProcessWithTokenW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithtokenw).

## Exact-head Windows regression diagnosed (2026-11-06; pending retest)

The first exact-head PR #110 Windows D QA [42173210302](https://github.com/i-shutov/tikzarium/actions/runs/42173210302) and hosted isolated MiKTeX [42173210406](https://github.com/i-shutov/tikzarium/actions/runs/42173210406) FAILED. Original artifacts #13481799664 and #13482028900 show CLI doctor and direct CLI compilation failed with Win32 **ERROR_BAD_LENGTH (24)** during a read-only token query; the direct MiKTeX subprocess on the hosted runner still produced Unicode PDF, but it is NOT TikZarium CLI acceptance and does not validate a safe child token. The pointer-aligned Rust `Vec<usize>` passed its rounded byte capacity instead of the exact 4-byte TokenElevation required length to `GetTokenInformation`. The Rust fix uses the exact requested length, keeps aligned storage, checks returned length, and adds a live Windows test. **This is a candidate diagnosis, not PASS until new-HEAD hosted Windows tests and originals confirm it.** A separate possibility is that an accurately elevated GitHub hosted runner subsequently rejects TeX as designed; in that case mark Windows CLI/PDF BLOCKED (do not change UAC or claim PDF PASS). Microsoft API reference: https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation.

### Hosted TeX execution boundary (not a workaround)

Original hosted [D06 #42173210406](https://github.com/i-shutov/tikzarium/actions/runs/42173210406) logs show MiKTeX reporting `security risk: running with elevated privileges` during setup, and the direct XeLaTeX proof succeeded despite TikZarium CLI failing. That historical direct PDF is **not** safe-child or release acceptance. The current candidate adds **early read-only process-token preflight** to both hosted Windows D06 and Windows D QA before installation, version probes or direct XeLaTeX: elevated/high/unknown token stops the Windows job and writes `BLOCKED_UNSAFE_TOKEN_NOT_RUN` JSON. Linux/macOS remain unchanged. A red Windows PDF QA under an unsafe token is intentional, not an invitation to bypass MiKTeX or reconfigure UAC. Separate genuine admin-account medium-filtered launch and approved same-account child must later demonstrate real GUI→PDF; neither is presently PASS.
